# Mythos Documentation Module Overview

## 1. Module Purpose
The Documentation module serves as the central knowledge repository and architectural reference for the Mythos system. It provides:
- **Design specifications** for adaptive systems (e.g., personality tuning, autonomic systems)
- **System architecture diagrams** and component relationships
- **Application registry** for Neo4j graph structures
- **Development guides** for frontend/backend integration
- **Configuration templates** for prompt systems and memory consolidation
- **Idea tracking** for future features and system evolution

This module ensures maintainability, traceability, and integration across the Mythos ecosystem by documenting technical decisions, system interfaces, and operational procedures.

---

## 2. Architecture Overview
The module is organized as a collection of markdown/JSON files with distinct functional layers:

### Core Structure
```
docs/
├── ADAPTIVE_TUNING.md       # Personality tuning system design
├── APP_REGISTRY.md          # Neo4j application registry
├── ARCHITECTURE.md          # System-wide architecture
├── AUTONOMIC_SYSTEM.md      # Autonomic system design
├── COMMAND_CENTER_DEV_GUIDE.md  # Frontend architecture
├── CONVERSATION_ENGINE_SPEC.md  # LLM interaction design
├── DOCS_LIBRARIAN_SPEC.md   # Documentation management
├── IDEAS.md                 # Feature proposals
├── IRIS_MEMORY_CONSOLIDATION_PIPELINE.md  # Knowledge evolution
└── IRIS_SYSTEMS.json        # System status tracking
```

### Data Flow
1. **Design Documentation** → **Configuration Files** (YAML/JSON)
2. **System Specifications** → **Code Implementation** (e.g., `prompt_assembler.py`)
3. **Runtime Data** (PostgreSQL/Neo4j) → **Documentation Updates** (via `docs-librarian` scanner)
4. **User Interactions** → **Session Tuner Analysis** → **Personality Slider Adjustments**

---

## 3. Key Components

| Component | Role | Key Files |
|---------|------|-----------|
| **SessionTuner** | Real-time personality adjustment | `ADAPTIVE_TUNING.md`, `core/session_tuner.py` |
| **AppRegistry** | Neo4j application tracking | `APP_REGISTRY.md`, `db_manager.py` |
| **ConversationConfig** | Structured LLM interaction | `CONVERSATION_ENGINE_SPEC.md`, `prompt_assembler.py` |
| **DocsLibrarian** | Documentation management | `DOCS_LIBRARIAN_SPEC.md`, `docs-librarian` CLI |
| **IrisMemoryPipeline** | Knowledge evolution system | `IRIS_MEMORY_CONSOLIDATION_PIPELINE.md`, `iris_sovereign_dataset.json` |

---

## 4. Design Patterns

| Pattern | Usage |
|--------|-------|
| **Singleton** | `SessionTuner` ensures single instance for session management |
| **Observer** | `SessionTuner` observes user responses to adjust sliders |
| **Component-Based** | React frontend in `COMMAND_CENTER_DEV_GUIDE.md` |
| **Factory** | `docs-librarian` processes files based on metadata |
| **Chain of Responsibility** | `ConversationConfig` applies layered prompt rules |

## 5. Data Model

### Configuration Files
- **YAML**: 
  - `prompts/personality.yaml` (personality sliders)
  - `prompts/tuning_rules.yaml` (adjustment rules)
- **JSON**:
  - `IRIS_SYSTEMS.json` (system status tracking)
  - `iris_sovereign_dataset.json` (training data)

### Database Structures
- **Neo4j**:
  - Labels: `GenPerson`, `GridNode`, `Document`, `Stream`, `Category`
  - Relationships: `PARENT_OF`, `HAS_METADATA`, `BELONGS_TO`
- **PostgreSQL**:
  - Tables: `scheduled_triggers`, `trigger_log`, `chat_messages`
